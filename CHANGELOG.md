## [0.1.0] - 2026-10-01
### Added
- Четыре задачи, каждая в двух реализациях (C17 и C++23):
    - **t1_dist_matrix_c\main.c и t1_dist_matrix_cpp\main.cpp**. программе даётся целое N (3 ≤ N ≤ 20) и она выводит
      матрицу попарных расстояний м-у вершинами правильного N-угольника единичного радиуса с центром в начале координат (в плоскости `z = 0`). в матрице главная диагональ - нули, у чисел - 3 знака после запятой. 
    - **t2_passport_c\main.c и t2_passport_cpp\main.cpp**. программе подаётся сначала название фигуры и потом кол-во 
      её вершин. выводится предложение типа «Фигура «звезда»: 7 вершин.», с именем, к-вом вершин и правильным склонением
      слова "вершина".
    - **t3_bbox_c\main.c и t3_bbox_cpp\main.cpp**. читает точки x y z из входного потока, до EOF.
      выводит количество точек, min/max по каждой из трёх осей (ограничивающий параллелепипед), центроид, среднее расстояние от точек до центроида (3 знака).
    - **t4_filter_c\main.c и t4_filter_cpp\main.cpp**. первым аргументом берёт радиус, вещественный `R > 0`. далее 
      читает точки x y z до EOF. выводит только те точки (3 знака после запятой), у которых расст. от центра меньше радиуса. 
- Общий модуль common:
  - **geometry** - ф-ции геометрического характера - распознавание точки из строки с x y z, нахождение расст. м-у двумя
    точками, нахождение центроида точек, нахождение координат вершины правильного N-угольника по номеру вершины и их общему количеству
  - **string_utils** - ф-ции для работы со строками - получение строки (для СИ-стороны), пустая ли строка?, обрезка
    пробелов по краям, есть ли 16ричный префикс? (для СИ-стороны), распознавание целого числа с учётом платформенных различий, распознавание радиуса, получение формы слова "вершина" в зависимости от кол-ва вершин, вывод версии программы (значение приходит из project(VERSION) через сгенерированный CMake-ом заголовок version.h).
  - **parse_codes** - заголовки. единый набор категорий ошибки разбора числа
  - **exit_codes** - заголовки. коды выхода для машинного канала, именованные неизменяемые значения
- Сборка
  - t1-t2 связываются со статическими библиотечными модулями из common. t1 - с geometry и string_utils, t2 - 
    string_utils
  - t3-t4 - с динамическим модулем, он состоит из geometry и string_utils

  И geometry.c/cpp / string_utils.c/cpp, и сами задачи включают заголовки geometry.h/.hpp и string_utils.h/.hpp;
  для обеспечения гибкости сборки (т.к. когда сборка статическая - то ф-ции библиотек помечать никак не надо. а когда динамическая, в библиотеке они должны быть экспортируемыми, а в программе - импортируемыми) вводится флаг COMMON_STATIC/COMMON_EXPORTS/ничего на этапе сборки. при первом варианте ф-ции не будут помечаться особым образом, а во втором - `__declspec(dllexport)`. если никакого флага нет, ф-ции будут помечены как `__declspec(dllimport)`
- Система сборки. CMake ([README.md](README.md), раздел "Структура" - описано назначение всех CMake-файлов в проекте) + пресеты Debug/Release (CMakePresets.json) - готовые пресеты для команд - полный набор пресетов описан в [README.md](README.md), разделы "vcpkg-часть, пресеты" и "Как собрать и прогнать тесты через CMake".
- Зависимости.
  - **vcpkg (manifest-mode)** - пакетный менеджер, для связи с внешними библиотеками и единообразия abi (через триплет
    единых опций для компиляции проекта и библиотеки). в режиме манифеста (vcpkg.json) - то есть зависимости хранятся 
    локально, для моего проекта (не глобально как при классич. режиме).
  - **закреплённый builtin-baseline + проверка reachability в CMakeLists.txt**. в vcpkg.json закреплён builtin-baseline 
    т.е. sha клона - фиксирует версии портов и рецепты для них (в ports/port_name/) - как собираются, с какими зависимостями, патчи, если они есть. в CMakeLists.txt расположена проверка достижимости этого sha с помощью git (т.е. если установленная версия vcpkg больше или равна baseline проекта - ок. если меньше - падение). проверка сделана раньше проверки в процессе vcpkg install, потому каскада падений, как при падении от проверки самим vcpkg, не будет.
  - **GoogleTest** - единственная внешняя библиотека на данный момент. с ней была проверена связь дымовой целью, но тесты
    с этим фреймворком пока не сделаны
- Тестовая инфраструктура:
  - **юнит-тесты** (parse_point, parse_int32, геом. ядро и т.д.) - тестирование отдельных ф-ций из общего модуля common.
    только pure-функции, не работающие с stdin/stdout
  - **acceptance-тесты** (через run_case/check, проверка stdout/stderr/exit-кода). тесты самих задач - подаётся вход,
    сверяется реальных выход и ожидание. внутри устроено так: программу запускает `run_case` (порождает процесс программы-задачи) со всеми входными параметрами - файл входа, выхода, ошибки, и пр. после завершения процесса снимается его код и становятся доступны файлы его выхода и его ошибки. `check` берёт ожидаемый код, файл (ошибки/выхода) и сравнивает это всё с ожидаемым кодом и файлом. и выдаёт вердикт - сошлось / не сошлось (и что именно не сошлось)
- Форматирование - через clang-format; можно либо `clang-format -i file`, либо через цель `cmake --build build/cfg --target format/format-check`. Первый из тестов в составе ctest - проверка формата clang-ом.
- Версионирование. Точка истины - в CMakeLists.txt - project(VERSION). Для каждой программы версию можно получить вызовом `prog_name --version`. Данный файл, CHANGELOG.md, хранит все смысловые изменения проекта.
- Документация - README. Содержит в себе разделы, необходимые для понимания проекта и корректной работы с ним
  - **Работа с числами в рамках проекта** какие числа ожидаются в какой задаче, какие классы ошибок может 
    вызвать неверно введённое число
  - **Структура** и **Прочее**. в "Структура" находятся файлы верхнего уровня или вложненные, с их описаниями. в 
    "Прочее" находятся папки, также с описанием
  - **Минимальные версии инструментов** - в данной таблице указаны миним. требуемые версии инструментов и версии, с
    с которыми реально проводилась работа
  - **vcpkg-часть** - описывается приготовление для работы с данными инструментом и его использование
  - **Как собрать и прогнать тесты через CMake** - сборка и тесты со всеми подробностями
  - **Версионирование** - где и как зафиксирована версия проекта, для каких модулей, и необходимые детали о
    версионировании, если они имеются
  - **Известные ограничения проекта** - несостыковки, неточности и подобные моменты, которые явно есть в проекте - не
    баги. возможно будут выровнены в будущем, если появится инструмент для этого / потребность / возможность

## [Unreleased]
### Changed
- юнит-тесты (c++ часть) переведены на GoogleTest с самодельных exe.
  сделаны suit-ы - OkCase, ErrCase и свои типы данных под них; 
  TEST_P - генерация класса по suit и INSTANTIATE_TEST_SUITE_P - статический объект, хранит данные для вызова; 
  регистрация в ctest через gtest_discover_tests (TEST_PREFIX + NO_PRETTY_VALUES); 
  читаемая диагностика через PrintTo/operator<<.
- выключен механизм vcpkg applocal для устранения конфликтов на параллельной сборке. копирование нужных библиотечных dll
  осуществляется через ф-цию deploy_vcpkg_dlls (tests/CMakeLists.txt) - ф-ция применяется для целей, которые используют
  фреймворк gtest. ф-ция windows-only - её тело обёрнуто в это условие, т.к. конфликты с vcpkg applocal возникают только
  на винде ввиду механизма связи с shared-библиотеками
- юнит-тесты C-части переведены на GoogleTest: файлы <функция>_c.cpp 
  (включают C-заголовок `common/*.h`, линкуются к `*_c_static`), старые самодельные tests/unit/*.c удалены;
- в common/geometry.h и common/string_utils.h добавлена обёртка extern "C": 
  C-библиотеки корректно связываются с C++-тестами; для C-потребителей инертно (скрыто за #ifdef __cplusplus).
