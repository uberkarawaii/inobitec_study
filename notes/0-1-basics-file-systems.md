## Древовидные структуры. Файловые системы.
Файлы. Форматы файлов (бинарный и текстовый). Расширения файлов. 
Привязка расширения к приложению. Файловые менеджеры (проводник в windows, far manager, total comander или др.), 
Текстовые файлы и редакторы (отдельные приложения типа notepad и встроенный в файловый менеджер). Кодировки символов.

### Файл
Файл возникает как следствие нужды хранить информацию. Потребность в хранении возникает из-за особенностей RAM и имеет свои условия:

- не всякому процессу достаточно виртуальной памяти, выделенной ему в RAM, для хранения информации;

- после окончания процесса очистится и его виртуальная память, а значит и данные, которые от породил.
  в то время как хотелось бы пользоваться этими данными и после того, как процесс окончился;

- к вирт. памяти процесса имеет доступ только сам процесс. но часто другим процессам тоже нужно получить доступ к этим данным.
  при хранеии в вирт. памяти это невозможно

При этом, ОС создаёт абстракции. Так и здесь, чтобый не уйти в впопросы физического хранения (как именно устроен накопитель, какие сектора / 
как осуществляется доступ по отступам / ...), вводится абстракция файла. Файл - это логичееский информационный блок, который порождается в ходе процесса. 
О нём можно думать как о разновидности адресного пространства, но в рамках долговременной памяти, а не оперативной.

### Расширения файлов. Привязка расширения к приложению
В рамках ОС оно не является обязательной частью имени файла (т.е. вполне может существовать файл "text_file"). 
Тем не менее, многие ОС поддерживают файлы с расширениями, типа main.c; расширений может быть и несколько - file.html.txt.odt - изначально html страница, 
переведённая в текст. файл, и потом в формат odt, и именно последнее расширение - это формат файла.

Расширение важно в след. моментах:

- чтобы напомнить, что это за сущность;

- для наглядности, т.к. на UI в зависимости от расширения ставятся разные иконки;

- для выбора приоритетной программы (графич. оболочки, Windows) - .docx откроется в Word, .txt - блокнот, и тд. хотя можно выбрать и иное приложение;

- для некоторого софта - codec не сможет проиграть текстовый файл, cl.exe не может откомпилировать файл .docx. 
  и если подать тому же cl.exe много файлов на вход, расширения помогут ему понять, что из этого можно компилировать, а что нет

Для ядра ОС они не являются столь значимой информацией - скорее это дополнение к имени, возможность сделать файл "уникальнее". 
Например, различить "main.c" и "main.obj", хотя оба - набор логич. блоков информации, оба называются main, но ввиду разного расширения они различимы.
При этом, для windows расширение имеет бОльшее значение - опред. типа происходит по нему, а на UNIX - по байтам в начале файла.

### Форматы файлов (бинарный и текстовый)
Обычные файлы - это файлы, содержащие инф. пользователя, подразделяются на текстовые и двоичные. 

Текстовый файл - осмысленный для человеческого глаза (если кодировка, в которой он сохранён, совпадает с кодировкой, выбранной в редакторе) текст из мн-ва 
строк. Каждая строка заканчивается или переносом строки (\n) и/или возвр. каретки(\r) (на винде - оба символа\r\n, на Unix - \n). 
Их легко редактировать, печатать, передавать по конвейеру при передаче результата одной команды в другую. 
Утилиты типа findstr работают именно с текстовыми файлами и ожидают строки для обработки. 


Бинарный файл - необходимый для использующего его программы, но непригодный для чтения файл. В нём нет как таковых "строк" и он не предназначен для обработки
в редакторе - это байты и если испортить даже малую их часть или сохранить бинарник в другой кодировке, то весь файл будет непригоден.

В первых байтах бинарного файла находится "магическое число" (4D 5A для .exe), по которому исполняющая программа понимает,
что это именно бинарник. У бинарного файла есть внутренняя стрктура: заголовок и тело. 

Заголовок: сигнатура, версия, размеры, смещения. Некая мета-информация, в т.ч. нужная для верной интерпретации тела файла. 

Тело: данные, секции, таблицы.

В бинарнике также отражено выравнивание - чтобы некие данные лежали по адресу, кратному некому числу байт (например, 4). 
Чтобы на прочтение процессор тратил минимальное кол-во операций (а не читал 2 слова и не вычленял из них данные, т.к. это дольше).

Unix-системе всё равно на расширение, важны только "магические числа"; на Windows же сначала см. расширение, если например это приложение, 
то для него при двойном клике будет вызван CreateProcess, и уже тот будет смотреть на "4D 5A" в заголовке и ему будет всё равно на расширение.


Любой файл - последоват. байтов - и бинарь и текстовый; так что текстовый файл - по факту подвид бинарного. 
Разница в том, для чего они назначаются и кто будет с ними работать. Например, CRuntime при работе с текстовыми файлами для совместимости с Windows 
при работе на ней меняет \n на \r\n при записи, и \r\n на \n при чтении. Если в таком случае воспринять бинарь как текст. файл, то внутри него 
могут быть попорчены байты, хотя это было не "\r\n" а некие адреса. Git делает ту же самую замену с текстовыми файлами (crlf will be replaced with lf).

От этого идёт и разный режим открытия - лучше не делать fopen("r"...) для бинарного файла, иначе будет плохо с \r\n и \n, как пример. 

### Файловые менеджеры (проводник в windows, far manager, total comander или др.)
#### Far manager

- работа с папками и файлами и встроенная командная строка. переключить отображение панелей - ctrl + o (под панелями - cmd)
 
- распараллеленный экран на две панели, переключение - tab; может быть и два диска, которые можно поменять при надобности

- открытие файлов в самом Far manager - f3 просмотр, f4 редактирование; при клике / enter - просмотр в специализированной программе

- множество кодировок при редактировании файла в самом Far

- возможность просматривать файл и как текстовый, и как бинарный (в hex формате) - shift + fn + f6, shift + fn + f4, 
  если до этого он был открыт для редактирования (fn + f4). 
  при просмотре файла как бинарника его нельзя редактировать, т.к. до этого делается fn+f6 - "View"

- удобное копирование (fn + f5) и удаление (fn + f8) файлов, предвариательно они выделяются через shift + fn; создание каталога через fn + f7

- выбор файлов по маске (+ на num lk) и парный deselect (num lk -)

- поиск файлов, содержащих заданный текст (alt + fn + f7); fn + f7 - поиск внутри файла

- можно работать с архивом как с обычной папкой, без распаковки

- можно подключать разные плагины, .dll, для добавления функционала - типа работы с архивами или изображениями

#### Total commander
Похож на Far Manager, но с графической оболочкой не в консоли.

- также есть разделение экрана на две панели

- также есть просмотр файла и как текста, и как бинарника в hex

- поддерживает множество кодировок

- есть сравнение файлов по содержимому, как fc в командной строке

- командная строка внизу экрана 

- работа с архивом - как с папкой, без распаковки

#### Проводник в Windows
Файловый менеджер с ui, ориентирвоан на визуальное восприятие больше, чем Far. Имеет меньше функций для взаимодействия с файлами

- однопанельный

- при открытии самого проводника он открывается либо в "Быстрый доступ", либо в "Этот компьютер"

- "быстрый доступ" - можно менять и файлы, и папки, которые в нём находятся

- в левой части экрана есть панель быстрого доступа. на ней также можно закреплять файлы и папки

- по умолчанию скрытые файлы не отображаются, но это можно изменить

- можно упорядочивать / фильтровать файлы по имени / типу / дате изменения / размеру

- на вкладке "вид" сверху можно поменять структуру отображения файлов 

- под верхней панелью есть строка, в которой можно перейти по опред. пути, в т.ч. к файлу. но cd / mkdir / ... команды выполнять нельзя.
  можно открыть cmd, набрав в верхней строке cmd + Enter 

#### Другие популярные файловые менеджеры (по совету deepseek: Double Commander и Directory Opus)

##### Double Commander
"Вдохновлён" Total Commander-ом.

- двухпанельный

- есть просмотр файлов как бинарников, в hex-режиме

- open-source, кроссплатформенный

- горячие клавиши похожи на то, что есть в Far (deepdeek: "это стандарт двухпанельных файл. менеджеров")

- есть встроенный текстовый редактор с подсветкой синтаксиса

- работа с архивами как с папками, без распаковки

- поиск файлов с заданным текстом

- поддерживает работу с изображениями - просмотр миниатюр и встроенный viewer

- внутри одной панели может быть открыто несколько вкладок 

##### Directory Opus

- коммерческое ПО, самое многофункциональное из двухпанельных FM на Windows

- все компоненты можно кастомизировать - расположение панелей, горячие клавиши, меню, и т.д.

- скриптование: можно написать свой скрипт (VBScript, JScript, PowerShell, и собств. скрипт язык) - типа "переименовать файл, скопировать его ..."
  потом этот скрипт можно добавить на панель и выполнять по двойному клику

- виртуальные папки. по факту несуществующая папка, но она отображается и внутри неё находятся ссылки на файлы, которые были отобраны по 
  некому фильтру. это именно ссылки, не копии

- работа с облаками типа OneDrive

- группировка файлов: с подведением итога по размеру; по произвольному полю (с заголовками групп).
  и их продвинутая сортировка: можно задавать цвет файлам назначенной категории; несколько усл. отбора через логич. выражение;

- есть также, как и у предыдущих менеджеров: работа с архивами, поиск, сравнение

### Текстовые файлы и редакторы (отдельные приложения типа notepad и встроенный в файловый менеджер)

#### отдельные приложения - notepad.exe
Открывается в отдельном окне. Минимальный функционал (не подчёркивает ошибки в коде или опечатки в словах).
По BOM пытается угадать кодировку файла, и если он сохранён без BOM, то открывает как ANSI, даже если там не ANSI.
Нельзя на лету сменить кодировку - нужно пересохранить файл в нужной кодировке. Кодировка файла будет изменена и тогда будет корректное отображение.
При сохранении можно случайно сохранить в неверной кодировке - т.к. в "Сохранить как" стоит та кодировка, которую блокнот сам "угадал".

До Windows 10 notepad не поддерживал utf-8 без BOM и дописывал эти BOM-байты, что например могло ломать компиляцию.

#### встроенные в FM (на примере far manager)
Открывается в том же окне. Также минимальный функционал.
Открывает файл в той кодировке, в которой он есть. Можно сменить кодировку отображения - именно то, что выводится на экран.
При этом сама кодировка файла останется неизменной.

**Far-manager - это hex-viewer - он просматривает именно байты (может отразить и в кодировке, но по сути - байты). Поэтому есть hex-режим**

**Notepad - не hex-viewer. Он всегда считает, что просматривает текстовый файл в какой-то кодировке, не байты.**

### Кодировки символов

КОДОВЫЕ ТАБЛИЦЫ

В основе кодировки есть таблица, сопоставление "число (биты, код символа) - символ". Последовательность битов, при этом, не всегда имеет одинаковую длину.
Естественно, нужно иметь единообразную "таблицу кодировки", иначе обмен информацией станет невозможным.

Комп. технологии активно развивалсь в США -> ASCII (american standart code for inform. interchange). 
Там только латнские символы англ. алфавита. Для их кодирования (+ первые 31шт на спецсимволы - /r ...)
выделяется 7 бит. Они влезают в 1 байт - мин. ячейка памяти для адресации и одна ячейка остаётся пустой (в неё можно было записывать некую слуюебную инф.)

потом компьютеры пришли в другие страны, и этот бит решили приспособить под новые символы.
сделали кодовые страницы ASCII. первые 128 - обычные ASCII символы. а остальные 128 - специфичные для разных стран.
и разные люди делали эти кодовые страницы для букв одинак. алфавитов, но ставили их в разном порядке. и 128 симв. не было достаточно для всех алфавитов мира.

пришли Windows и сделали на основе ASCII ANSII. для каждого алфавита была своя код станица: windows 125x, где x - код страны.
для азиатских алфавитов не хватало символов, была придумана переменная длина кода. но никто не использовал эту кодировку повсеместно.
единообразия не было.

**ANSII и ASCII - это и кодировка и кодовая таблица**

для единообразия был придуман Unicode - международный стандарт. его идея - неограниченное число символов. **Unicode - это не кодировка, а именно таблица/** 
первые 128 символов совпадают с ASCII. проблемы:
 
1. в юникоде минимум 16 бит на символ. но для англ. алфавита и 7 бит достаточно. поэтому продолжалось использование ASCII

2. есть прямой порядок байт, и есть обратный (big / little endian) - там меняется и расположение бит внутри байта, и, соотв., порядок чтения байтов
   и при пересылке текста это могло вызывать проблемы с приходом юникода.
   т.к. при ASCII любой символ стабильно занимал 1 байт и он не может быть прочитан "наоборот", т.к. он всего один. 
   а в юникоде байтов стало от 2х - как понять с какого конца читать? 

КОДИРОВКИ (для записи кодов символов в память)

**Всё, описанное далее, - именно кодировки. Не таблицы**

**UCS-2 universal coded character set**: всегда 2 байта. в начало текста всегда добавлялись ведущие байты - BOM - unicode byte order mark.
FE FF - big endian, FF FE - little endian.
так, строка начала занимать на 2 байта больше. это тоже перерасход по памяти

**UTF-8** - минимальная длина - 8 бит. но длина переменная, до 4 байт. первые 128 символов по 1 байту - смиволы ASCII, без перерасхода.
остальные, с 2 байт до 4 байт - символы других алфавитов. проблема с BOM который занимает место, решена так: в первом байте символа ставится одно из четырёх

- 0 - 1 байт 
- 110 - 2 байта (второй байт начинается с 10, т.к. это продолжение символа)
- 1110 - 3 байта (2 и 3 байт начинаются с 10)
- 11110 - 4 байта (2, 3, 4 байт начинаются с 10)

и байты после первого, если их 2 и более, начинаются с 10 - указывает на то, что это продолжение кода символа.

так, если прямой порядок чтения - видим что одна из 4х нач. комбинаций - хорошо, читаем. 
если обратная последоват. чтения - видим например, что символ начался с 10 - это невозможно, в начале обязательно должно быть 0 / 110 / 1110 / 11110. 
идём назад, пока не найдётся одна из 4х комбинаций начала

динамическая обработка т.к. длина символов переменная, сделала обработку символов медленнее.

**UTF-16**: хранение более чем 2 байтов и обратная совместимость со старыми 2 байтовыми кодировками.
т.к. двухбайтовые символы всегда идентичны символам UCS-2, новые символы хранятся в 4 байтах.

- диапазон для 2байтовых: 0x0000 - 0xffff
- диапазон для кодов более 2байт: 0x10000 - 0x10ffff; где 0х10000 = 1 0000 0000 0000 0000, а 0x10ffff = 1 0000 1111 1111 1111 1111 

в нормальном диапазоне 2байтовых символов есть поддиапазон неиспользуемых кодов: d800 - dfff для кодирования суррогатной пары (тех самых 4байтовых чисел).
если при чтении попадается число из такого диапазона, то это означает, что нужно прочитать ещё 2байта.

суррогатная пара делается так. например, берётся символ из юникода, который занимет более 2байт. из него вычиается 0x10000 (= 1 и 16 нулей в 2сс) потому что это первое число из
диапазона для кодов более 2байт. далее, получается так, что у нас остаётся 20 и менее бит. т.к. 0x10ffff - 0x10000 будет 20 бит. 

эти 20 байт делятся пополам, по 10 бит. левые 10 - старший суррогат, правые - младший. 

- старший суррогат до вычитания: 0000 000000| - 1111 111111|
- младший суррогат до вычитания: |00 00000000 - |11 11111111

к старшему прибавляется 0xd800 - начало "запретного" диапазона. 
к младшему прибавляется 0xdc00 - середина "запретного" диапазона. в итоге старший суррогат получается в диапазоне d800 - dbff, а младший - dc00 - dfff

чтение будет по 2 байта и будет понятно, из обычного диапазона байты или нет. нужно читать ещё 2 байта или нет

Также, в UTF-16 есть BOM-байты, чтобы понять, откуда начать читать.

UTF-32: 4 байта и BOM. Т.к. в UTF-16 переменная длина, то это увеличивает время обработки. Поэтому в ютф-32 постоянная длина

СФЕРЫ ИСПОЛЬЗОВАНИЯ

- UTF-8 без BOM: файл с ним весит мало, так что используется для передачи по сети.

- UTF-16, UTF-32: скорость обработки выше, поэтому, например, языках программирования (java - utf16, python - utf32).

### Побочная информация 

- почему компьютер читает не по одному байту. потому что память так устроена, что это не "линия", а "таблица". и считывание - именно построчно - т.е. может 
  быть 4 по байта или вроде того. пример от deepseek про эти отступы
```
struct Example {
    char a;   // 1 байт
    int  b;   // 4 байта
};
```
  компилятор положит в память не так: 
```
0  1    2     3
a b[0] b[1]  b[2]
```
  а вот так, где "-" и есть отступ, то есть незначащие байты, мусор 
```
0  1    2     3    4   5   6   7
a  -    -     -  b[0] b[1] b[2] b[3]
```
  struct по итогу займёт 8 байт, а не 5 байт, как в ней занимают данные

- также имеет значение утсройство DRAM - на нахождение строки нужно много времени. 
  поэтому за одно обращение может быть прочитано 1Кб и из них выбрано нужные 4байта.
  это особенность физ. устройства DRAM

- если бы адресация была побитовой, то адресную шину пришлось бы расширить с 32 линий до 35 
  (потому что сейчас адресация 1 байт, в нём 8 бит - как бы надо умножить на 2 3 раза, т.е. добавить 3 разряда).
  для каждой линии нужен контакт на процессоре - тоже надо увеличивать, и ещё нужен контакт на модуле памяти.
  работа с одним битом происходит редко, и есть битовые маски для этого. они покрывают потребность работы с битами по отдельности

- мультиплексор - устройство для нахождения (декодирования) ячейки по адресу, который ему пришёл, и замыкания именно на этой ячейке, 
  чтобы напряжение от неё могло быть передано 

- почему отображение бит идёт в 16СС хотя компьютер считает в 2СС? просто чтобы нам было удобнее воспринимать т.к. нашему глазу
  2СС менее удобна нежели 16СС. поэтому байт (8 бит) бьётся на 2 части и получается два 16ричных числа
